# البنية الهندسية والمعمارية للنظام - v2.0 Enterprise Edition

يوضح هذا المستند التصميم الهيكلي البرمجي لنظام إدارة معرض السيارات v2.0 Enterprise Edition بالاعتماد على بنية المعمارية النظيفة (Clean Architecture) وتصميم النطاق الموجه (Domain-Driven Design).

---

## 1. طبقات النظام (Clean Architecture Layers)

تم تقسيم الحل البرمجي إلى 4 مشاريع أساسية لضمان فصل المسؤوليات بالكامل وسهولة الصيانة والاختبار والتوسيع المستقبلي:

```
                  +-----------------------------------+
                  |             API Layer             |
                  |     (Controllers, Middlewares)    |
                  +-----------------------------------+
                                    |
                                    v
+------------------+      +-----------------------------------+
|  Infrastructure  | ---> |         Application Layer         |
|  (EF Core, DB,   |      |   (MediatR CQRS, Validators)     |
|   Identity, Redis)      +-----------------------------------+
+------------------+                        |
                                            v
                                  +---------------------------+
                                  |        Domain Layer       |
                                  |  (Entities, Enums, Rules) |
                                  +---------------------------+
```

### أ. طبقة النطاق (Domain Layer)
* **الوظيفة**: قلب التطبيق الذي يحتوي على الكيانات، القواعد الحاكمة للأعمال، الـ Enums، والاستثناءات الخاصة بالنطاق.
* **الاعتمادات**: لا تعتمد هذه الطبقة على أي مشاريع أخرى أو حزم خارجية (مستقلة تماماً).
* **المكونات الأساسية**: `Account.cs`, `JournalEntry.cs`, `Vehicle.cs`, `User.cs`.

### ب. طبقة التطبيق (Application Layer)
* **الوظيفة**: تحتوي على واجهات الاستخدام (Interfaces)، منطق التطبيق، معالجة الأوامر والاستعلامات (CQRS using MediatR)، ومحركات التحقق من المدخلات (FluentValidation).
* **الاعتمادات**: تعتمد فقط على طبقة الـ **Domain**.
* **المكونات الأساسية**: `CreateJournalEntryCommand.cs`, `GetTrialBalanceQuery.cs`, `IApplicationDbContext.cs`.

### ج. طبقة البنية التحتية (Infrastructure Layer)
* **الوظيفة**: توفر المحركات الفعلية للواجهات المعرفة في طبقة التطبيق. تتعامل مع قاعدة البيانات (EF Core, PostgreSQL)، التخزين المؤقت (Redis)، التشفير، والهوية (Identity Service, JWT).
* **الاعتمادات**: تعتمد على طبقة الـ **Application**.
* **المكونات الأساسية**: `ApplicationDbContext.cs`, `AuditableEntitySaveChangesInterceptor.cs`, `IdentityService.cs`.

### د. طبقة واجهة برمجة التطبيقات (API Layer)
* **الوظيفة**: بوابة العبور للتطبيق والمستهلك الخارجي. تتعامل مع طلبات الـ HTTP واستجاباتها، وتوثيق الـ API (Swagger)، والـ Middlewares مثل معالجة الأخطاء.
* **الاعتمادات**: تعتمد على طبقة الـ **Infrastructure** وطبقة الـ **Application**.
* **المكونات الأساسية**: `AccountingController.cs`, `AuthController.cs`, `ExceptionHandlingMiddleware.cs`.

## 2. تدفق البيانات والتحكم (Request Flow / CQRS Pattern)

تعتمد البنية على فصل القراءة عن الكتابة (CQRS) لتسريع الأداء وتسهيل الصيانة:

1. **الـ Command (إنشاء/تعديل البيانات)**:
   * يرسل المتصفح طلب POST يحتوي على البيانات.
   * يستقبل الـ API Controller الطلب ويرسله عبر MediatR.
   * يقوم FluentValidation بفحص القواعد (مثل: هل القيد متوازن؟).
   * يقوم الـ Handler باستدعاء الكيانات والقواعد من الـ Domain وتطبيق التغييرات.
   * يقوم الـ Interceptor بحقن حقول التدقيق والتحقق من القواعد المالية الصارمة (منع التعديل/الحذف).
   * يتم حفظ البيانات في PostgreSQL.

2. **الـ Query (قراءة البيانات والتقارير)**:
   * يرسل المتصفح طلب GET.
   * يقوم الـ Controller بإرسال الاستعلام.
   * يقوم الـ Handler بالاستعلام المباشر من قاعدة البيانات (أو خادم الكاش Redis لتسريع القراءة).
   * يتم إرجاع النتيجة كـ DTO خفيف خالي من المنطق المعقد.

## 3. قابلية التحول إلى الخدمات المصغرة (Future-Ready Microservices)

تم تصميم النظام الحالي كـ (Modular Monolith / Service-Oriented Architecture) بحيث يمكن في المستقبل فصل أي جزء منه كـ Microservice مستقلة في غضون أيام قليلة للأسباب الآتية:
* **عزل قواعد البيانات (Schema Isolation)**: تم عزل جداول المحاسبة والمخزون والهوية منطقياً في قاعدة البيانات.
* **فصل الاعتماديات (Dependency Inversion)**: تتواصل الطبقات عبر واجهات مجردة، مما يتيح استبدال الاتصال المباشر بقاعدة البيانات باتصال شبكي (gRPC or HTTP) دون أي تعديل في طبقة منطق التطبيق.
* **عزل الخدمات في Kubernetes**: يتم تشغيل التطبيق في Kubernetes Pods مع إمكانية توزيع الأحمال والتوسيع التلقائي بشكل مستقل لكل حاوية.
